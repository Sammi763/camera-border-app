# macOS arm64 胶片校色试用 0.1.2

0.1.2 增加了正片调整滑杆、拖动快显、松手精算和彩负密度建议。快显从基础正片生成
1024 像素长边的线性浮点层，显示端输出 8-bit sRGB PNG，精确预览仍输出 16-bit PNG。
直方图在精确结果后更新，队列缩略图在调参停稳一秒后更新。片基、中性取样、100% 像素检查和导出读取完整源图。

阶段缓存可以从已有基础正片直接开始调整。源事实按内容版本复用，预检无需重新解码
已经读取过的原图。FFF 的无压缩交错 RGB16 单条带逐行读取，其他布局继续走 ImageIO。
大区域片基中位数用固定大小的缓冲精确求取。源文件和参考帧仍使用 SHA-256 校验。

## 复现 2338 卷彩负偏暗

1. 选择「彩色负片转正」。
2. 打开「框选片基」，框选最后一格下面的均匀橙色片基，避开编号和扫描仪边框。
3. 打开「框选画面建议密度」，框选第一格画面的有效区域，点击「应用密度建议」。
4. 这张样片在上述区域给出密度上限约 0.79，可用同卷 TIFF 成片人工核对观感。

原配方用左上角画面作为片基。实际第一格抽样中，旧片基使三个通道约 34%–41% 的
像素遇到透过率上限并归到黑位。重新取样后，该比例低于 0.3%。默认上限 3 使所剩
中间调继续偏暗。密度建议只在用户确认后应用，数值取决于所框画面。FFF 输入域仍是
人工声明，物理标定与专属胶卷模型继续单独验收。

## 安装包与像素回归

- 安装包 `Camera-Border-0.1.2-arm64.dmg`，SHA-256
  `2ce44da80941cad2bf1c47ffc97e10697ca1ab4ad0d7c985482809c22c085ad3`，构建提交 `9acfce2`。
- 从只读 DMG 复制安装副本，使用随包 Java 11 和隔离应用数据启动。相同配方批量
  导出两张 4795 × 16857 TIFF 耗时 46.8 秒，包含提交和任务轮询。
- 独立回读确认两张 TIFF 都是 RGB 三通道 16-bit、方向 1、线性 Rec.2020 ICC，
  像素条带 SHA-256 与 0.1.1 基准逐位一致。原 FFF 文件 SHA-256 未变。
- 本机证据在 `.local/film-performance-012/`，包含预览基准、批量导出、样片校色
  对照与独立回读记录。

## 性能验收

同一台 32 GiB Apple M2 Pro。以下像素与性能基准使用构建 `e503b21`，最终包增加了前端
缩略图合并，沿用同一 Java 处理代码。每种输入执行三次冷阶段缓存启动，并记录
30 次热调参。耗时范围从安装包内提交请求到图片解码及浏览器呈现，拖动、松手和过期
请求行为另由工作台验证。峰值 RSS 每 250 毫秒采样，取同一时刻进程树之和。

| 输入 | 0.1.1 热调参 P95 | 0.1.2 快显 P95 | 0.1.2 冷预览中位数 | 0.1.2 精确预览中位数 |
| --- | ---: | ---: | ---: | ---: |
| 5035 × 3339 扫描 JPEG | 3.22 秒 | 1.03 秒 | 5.50 秒 | 1.61 秒 |
| Sony ARW | 2.62 秒 | 1.40 秒 | 5.64 秒 | 2.22 秒 |
| 8080 万像素 FFF | 对照批次超时 | 3.05 秒 | 33.25 秒 | 4.16 秒 |

JPEG 和 ARW 的冷预览与精算中位耗时回退均在目标范围内，固定配方的精确 PNG 摘要
与 0.1.1 一致。快显 P95 高于 0.5/0.8 秒目标，主要等待发生在引擎端。大 FFF
原尺寸导出流程的峰值 RSS 为 8.11 GiB，高于 5.8 GiB 目标。旧包的大 FFF 热调参
基准超时，导出耗时也缺同口径重复测量，这两项相对速度仍待验收。32 GiB 本机
数据仅涵盖 macOS arm64。

最终安装副本复测了彩负取样和拖动。重新取样生成 0.79 的密度建议并应用。大 FFF
连续拖动提交了两次主快显，松手提交最终 2.94 EV 的精确预览，随后队列只刷新一次
缩略图。原冒烟断言把最后一次缩略图当成主预览，已修正过滤方式，并独立核对原始
请求记录。
