# ADR-0008：调参合并、内存准入与分阶段缓存

- 状态：已接受
- 日期：2026-11-12
- 关联：[ADR-0007](0007-explicit-film-digitization-mode.md)、[ARCHITECTURE.md §4](../ARCHITECTURE.md)、[java-engine/README.md](../../java-engine/README.md)

## 背景

底片数字化模式需要同时处理 24–45MP 照片的真实 RAW 解码、负片转正、正片调整、分析、
预览编码和原尺寸导出。连续拖动控件会快速产生多个 RenderRecipe 快照；如果每个快照都
独立解码和转正，既浪费 CPU，也会让多个全幅 float32 缓冲同时存活。与此同时，RAW helper
是独立子进程，Java 堆预算不能代表整个任务的峰值内存。

本轮不改变算法、float32 工作精度和原尺寸语义，只减少重复计算并限制同时存活的资源。

## 决策

### 1. 前端只提交稳定快照

- 控件值、编辑状态和撤销历史仍立即更新；引擎请求统一经过 `TuningScheduler`。
- 拖动期间 leading + trailing 节流，最多每 250ms 提交一次；`pointerup`、`focusout`、
  `change`、Enter 和 `flush()` 立即提交最新快照。
- 每个视图只保留一个在途请求和一份最新待提交快照；相同内容键不重复提交。
- 主预览、阶段对比和直方图共享 `PreviewState.engineRecipe`、`engineClientId` 和
  `engineGeneration`。主预览先请求，分析等待对应预览完成；等待期间保留上一张正确画面。
- 切图、关闭底片模式或卸载视图时中止在途请求、清除计时器，并调用
  `DELETE /api/film-requests/{clientId}?generation=n`。
- 取消/被替代是正常状态，不显示“引擎不可达”。

### 2. 后端统一重型任务闸门

`FilmTaskScheduler` 是唯一的重型任务串行点，取代 `FilmRequestGuard` 的旧信号量和
`FilmProcessingPipeline` 的 `processingSlot`：

- 全引擎同一时刻只执行一个预览、分析或导出项。
- 每视图每类交互操作只保留最新待处理项；同类相同内容键的重复请求共享结果。
- 等待任务总数上限 16，超出返回 `429 / FILM_BUSY`。
- 交互优先；存在导出等待时，连续执行最多两个交互任务后必须执行一个导出项。
- 新代次取消该视图旧代次的等待任务与执行中计算；导出项不登记视图，不因调参取消。
- 取消检查保留在文件摘要、像素循环、helper 等待和编码写出路径；HTTP abort 不被当作
  计算已经结束。

### 3. 内存准入按阶段估算

- 分配大数组前探测输入尺寸：TIFF 解析头信息；真实 RAW 调用
  `film-raw-helper --probe --input <path>`，只读取尺寸和源事实，不 unpack、不去马赛克、
  不生成像素输出。未知尺寸明确失败。
- 估算同时存活的 RAW 原生 helper、RGB16、float32 工作图、参考帧、几何/放置、装饰层、
  编码与输出缓冲；共享数组只计一次，取最大同时存活量并增加 25% 余量。
- 预算：
  - `B = min(4GiB, 物理内存的 25%)`，物理内存不可识别时回退 `2GiB`；
  - `H = min(B, JVM 最大堆的 70%)`；
  - `C = min(1.5GiB, H 的 50%)`，包含在 H 内。
- 每次执行前回收过期/未被租约固定的缓存；预算不足时再回收本任务不复用的未使用条目。
- 缓存字节计入 H；准入同时检查 Java 峰值（H）和含 helper 的总峰值（B）。
- 回收后仍超预算返回 `422 / FILM_MEMORY_BUDGET_EXCEEDED`；队列满或暂时繁忙返回
  `429 / FILM_BUSY`。不静默降低精度或输出尺寸。
- 预算租约覆盖解码、分析、编码和写出的完整生命周期，所有退出路径统一释放。不调用
  `System.gc()`，不把估算宣称为应用 RSS 硬上限。

### 4. 分阶段浮点缓存

新增 `FilmStageCache`，与预览 PNG、前端 URL 缓存分开：

| 阶段 | 内容 | 失效条件 |
|---|---|---|
| `raw-linear` | 有向线性工作图、解码及来源事实 | 源文件、解码参数、输入色彩声明、解码器版本 |
| `base-positive` | 光源、片基、密度处理后的基础正片 | 上游变化、负片参数、校准/参考帧变化 |
| `current-positive` | 正片曝光、曲线、色彩调整结果 | 上游变化、正片调整参数 |

- 阶段键使用规范化有效参数、上游键、源版本、算法版本、工作空间和实际处理尺寸；
  几何、边框、文字、Logo、输出格式不使照片阶段失效。
- 源文件和参考帧都使用 SHA-256 内容版本，不退化为路径/mtime/大小。
- 输出色彩空间不进入照片阶段键；本轮不缓存最终输出，避免预览与母版串用。
- 缓存图像只读共享；处理器不得原地修改输入。缓存条目返回防御性 SourceDecode 副本。
- 失败、取消后的半成品不入缓存。
- 全局按字节计量；优先保留 `base-positive` / `raw-linear`，先淘汰 `current-positive`，
  同优先级 LRU；正在使用的条目由租约固定。
- 空闲 120 秒后可回收，进程退出即清空，不写磁盘。超预算条目跳过缓存。
- `app.film.stage-cache.enabled=false` 可关闭缓存做逐位回归；预算和调度保护始终生效。

## 备选方案

- **只做前端防抖**：无法处理跨视图、重复请求和后端导出竞争；导出仍可能被调参饿死。
- **每个请求独立 Semaphore**：会出现多层串行锁，取消语义分散，无法统一公平调度。
- **把预算等同于 JVM 堆**：会忽略 LibRaw helper 和 Java2D 装饰层，无法解释 16GB 机器上的峰值。
- **只按最近一次请求计时**：无法区分缓存命中与真实重算，也不能证明正片曲线修改没有重做 RAW。
- **写磁盘缓存**：与本地优先、进程退出清空和隐私边界冲突。

## 后果

- 连续调参会合并为稳定快照，旧结果不会回写；导出等待有确定性上界。
- 阶段缓存显著减少 RAW 解码和基础转正，但缓存命中率受内存预算影响；缓存不足只影响性能，
  不影响正确性。
- 极端尺寸或几何组合在 16GB 机器上可能明确返回 422，而不是静默降级。
- 性能证据必须记录冷/热缓存、阶段命中率和 Java/Electron/Renderer/helper 内存；没有 16GB
  实机或所需样片时标记未验收，不能用 32GB 机器结果替代。
